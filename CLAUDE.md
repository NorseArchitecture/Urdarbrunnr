## What This Realm Is

Urðarbrunnr is **the well's record** — `Norse.Persistence`: the platform's persistence realm, scoped to all database and data-store activity, not just EF Core. `Norse.Persistence.EntityFramework.*` is today's live vendor family; a different ORM (Dapper), a native driver, or a document/search store (MongoDB, Elasticsearch) lands as its own sibling under `Norse.Persistence.*` — no separate realm, no new repo, the same drop-in pattern Heimdall used for FluentUI. It sits below Asgard and Svartálfheim, above Midgard.

## Architecture Facts (decided — do not re-litigate)

- **The provider seam's tier split is a compile-time gate:** `INorseEfMigrationProvider` adds no members over `INorseEfProvider` — it exists so registering a non-migration-capable binding (a future SQLite) against a migration host is a compile error, not a runtime surprise. Every binding is one sealed class with `public static Instance`; `NameRewriter` and `TemporalRealizationHook` have **no defaults** — every binding states its posture rather than silently inheriting a no-op.
- **Entities configure themselves:** `INorseEntity<TSelf>` carries a static abstract `Configure(EntityTypeBuilder<TSelf>)` — static, not instance-based like EF's `IEntityTypeConfiguration<T>`, so the generator never constructs an instance just to call it, and the compiler refuses a concrete entity without one. `RequireEntityConfigurationConvention` enforces colocation at model finalize; the generated `ApplyNorseConfigurations()` applies them.
- **Three registration surfaces, not one:** `AddNorseContext` (pooled, runtime hosts), `AddNorseContextFactory` (the pooled `IDbContextFactory` sibling — composition isolation for callers that must own context lifetime), `AddNorseMigrationContext` (non-pooled — a migration host runs once and exits, and pooled options are frozen).
- **The migrations generator's diagnostics are NORSE030–034:** no provider binding (030), more than one (031), no `ModelSnapshot` for a context (032), binding missing its `Instance` member (033), more than one `ModelSnapshot` (034 — reference order must never decide it). It walks compiled assembly symbols, never syntax trees.
- **Generator provenance, recorded once:** this realm shipped the platform's first Roslyn generator (2026-07-22, inside the retired `Design.PostgreSQL` package). The seam repackaging consolidated it provider-agnostic into `.Migrations`; the `gen/` restructure moved both generators into their own projects packed into their `src/` siblings. The mechanism never changed; where it lives did — don't re-litigate the credit or the moves.
- **Snake_case naming is in-house** (`NorseSnakeCaseNamingConvention`/`SnakeCaseNameRewriter` — no `EFCore.NamingConventions` dependency), expressed per binding: Postgres `LowerSnakeCase` (engine-native), SQL Server `null` (raw PascalCase; its temporal rename hook is inert **by construction** — `ApplyNorseProviderOptions()` only wires `EntityRenameHook` when `NameRewriter` is non-null). Three hardening fixes are load-bearing downstream: the EF migrations-history table is excluded from renaming entirely (renaming it desynced `HistoryRepository.TableName` and 42P01'd on first migrate); only a JSON-mapped entity's own **root** container column is renamed (nested renames crash EF 11 preview6's JSON query shaper — the `dotnet/efcore#37417` shape); and split-table fragments are named too (2026-08-06, `feature/snake-case-entity-splitting`).
- **`[FixedLength(n)]` only becomes `IsFixedLength()` on SQL Server** — Postgres's own docs say `character(n)` is a pure downside there. `NorseModelConventions.Apply()` registers the provider-correct `SequentialGuid` byte-order converter: `SqlServerSequentialGuidValueConverter` on SQL Server, `Rfc9562SequentialGuidValueConverter` everywhere else — this realm's first real code dependency on Svartálfheim's `Norse.Primitives`.
- **PII protection composes inside one converter:** `ProtectedPiiValueConverter<TPii>` is canonical wire string ∘ protect on write, unprotect ∘ parse on read — there is no converter-ordering problem because there is no second converter. The captured `IPersonalDataProtector` must be a singleton over singleton seam dependencies (EF caches the model per context type; the first-resolved instance serves every request — Identity's own capture pattern). `ProtectPiiScalars()` is called after `base.OnModelCreating` and wires the converter onto every struct-typed `IPiiScalar` property; a decrypted value that no longer parses is storage corruption and **fails loudly**. NORSE061 (Svartálfheim law) requires every PII-typed member to declare a retention policy — the fixture entity itself had to comply.

**Temporal (system-versioned) tables — chassis capability, never hand-rolled SQL.** Section references are the 2026-08-04 spec's:

- **Opt-in is one marker.** `ITemporalEntity` is an empty interface, no members ever — `system_period` never enters the CLR type, a wire `[DataContract]`, or a WASM payload (§2.1). Adoption is two acts: add the marker, run `dotnet ef migrations add` (§5). Brownfield tables take the same path as greenfield.
- **`TemporalEntityConvention` is the one validation point:** at model finalize each marked entity must have a primary key, must not be owned or JSON-mapped, and its derived names (`{table}_history`, `{table}_timeline`, `{Table}History`) are reserved — collisions throw by name at startup, not late in a migration (§2.2). Validated entities are stamped `Norse:Temporal` (`NorseAnnotationNames`, public because provider packages read it).
- **Stamp-then-realize, one pass, not a style choice:** the convention invokes the binding's `TemporalRealizationHook` immediately after each stamp because plugin-added finalizing conventions run *before* context-added ones — an independent realization convention would read the annotation before it exists. The hook reaches the context through `NorseTemporalRealizationOptionsExtension`, deliberately carrier-only.
- **SQL Server realizes in the model:** EF-native `IsTemporal(true)`, periods `SystemPeriodStart`/`SystemPeriodEnd`, history `{Table}History` (§4). **Split-table + temporal is a model-finalize error there**, dismissible only via `TemporalParkedOnSqlServer()` — a greppable declared divergence that skips temporality on SQL Server alone. Re-entry trigger: delete the park the day [dotnet/efcore#26457](https://github.com/dotnet/efcore/issues/26457) ships (the NRE behind it is [#30366](https://github.com/dotnet/efcore/issues/30366)).
- **PostgreSQL realizes nothing in the model — three `ReplaceService` seams, unconditional in `Configure`:** `NorseNpgsqlAnnotationProvider` (projects the marker onto the **root** relational table only, so split fragments never inherit it), target-model consultation inside `NorseNpgsqlMigrationsSqlGenerator`, and `NorseNpgsqlMigrationsAnnotationProvider.ForRemove` for the drop side where `DropTableOperation` carries no annotations at all.
- **The apparatus is Norns Model B** (`TemporalSqlEmitter`, one self-contained method per §3.1 element): `system_period tstzrange`, `{table}_history` under `PRIMARY KEY (…, system_period WITHOUT OVERLAPS)`, a hardened `SECURITY DEFINER` versioning function (`search_path` pinned to `pg_catalog`, `EXECUTE` revoked from `PUBLIC`), INSERT/UPDATE/DELETE triggers, and a `{table}_timeline` view with explicit column lists.
- **PG19 is a floor asserted in-migration** — `server_version_num >= 190000`, an idempotent `btree_gist` guard with a named provisioning diagnostic, and (when neither operation nor model names a schema) a `current_schema() = 'public'` assert — emitted once per migration batch, at the first temporal table. Evolution paths skip the prelude deliberately.
- **`now()` appears nowhere; `system_period` is database-owned on every verb** (amended 2026-08-05, INSERT guard): a BEFORE INSERT branch RAISEs on a client-supplied period and assigns `tstzrange(clock_timestamp(), 'infinity')` — a `DEFAULT` clause was tried and dropped because a BEFORE trigger can't distinguish its own default from a client value. The monotonicity clamp keeps every history period strictly positive; no-op suppression means a no-change UPDATE writes nothing. Accepted residual: data-only `pg_restore`/`COPY` into a live temporal table RAISEs — the DBA path is `--disable-triggers`.
- **Transitions and evolution both ship** (§3.3–§3.4): enable-on-existing backfills from a **single** captured `clock_timestamp()`; disable and entity-drop are visible destruction as plain statements. Column operations emit in the fixed drop-view-first order (the only appliable one); history mirrors name and store type only. `RenameTable` is the one exception — rename both tables in place, then explicitly retire and recreate every derived object (Postgres keeps a renamed table's triggers under old names bound to the old function). Batches group per table by target name.
- **What the generator refuses, it refuses by name, before emitting SQL:** marker transition combined with column operations on the same table, primary-key changes on a temporal table, schema moves. Each diagnostic names the sanctioned path. Silently-wrong history constraints are the one outcome this design will not ship.
- **Proof is chassis-out, no mocked databases:** snapshot suites over EF's real differ (`TemporalCreateTableSqlTests`/`TemporalTransitionSqlTests`/`TemporalEvolutionSqlTests`), live application (`TemporalEvolutionLiveTests`) so snapshot-green-but-unappliable DDL cannot ship, and the 13-fact §3.2 semantics suite (`TemporalApparatusIntegrationTests`). Recorded deviation from spec §6 item 3: the live tests live in `Persistence.EntityFramework.PostgreSQL.Tests`, not a new project.
- **Downstream is not this realm's gate:** adopting realms' enablement and Bifröst's replica proof belong to those realms.
