## 1. What This Repository Is

Urðarbrunnr is **the well's record** — `Norse.Persistence`: the platform's persistence realm, scoped to all database and data-store activity, not just EF Core. `Norse.Persistence.EntityFramework` is today's live vendor family — entity base types, `DbContext` foundations, conventions, value converters, and the migrations chassis, the EF Core foundation that Midgard's concrete repository implementations ride on, governed by the contracts Asgard declares — but it is one branch, not the ceiling. A different ORM (Dapper, NHibernate, SqlSugar), a native driver that bypasses an ORM entirely, or a document/search store (MongoDB, Elasticsearch) lands here the same way Heimdall took on FluentUI: drop in the vendor-specific `.csproj` and package references as a sibling under `Norse.Persistence.*` (`Norse.Persistence.Dapper`, `Norse.Persistence.MongoDB`, …), wire it up, done — no separate realm, no new repo. In the dependency chain it sits below Asgard and Svartálfheim, and above Midgard.

**Five assemblies are live**, built around a provider seam (`../Glitnir/docs/Urdarbrunnr/specs/2026-07-27-ef-provider-seam-repackaging-design.md`), the repackaging that superseded the four-plus-per-provider-generator shape shipped as Tasks 3–6 of the cross-realm migrations framework rollout (`../Glitnir/docs/Platform/plans/2026-06-28-migrations-framework-identity-schema.md`):

- `Norse.Persistence.EntityFramework` — the neutral foundation: `INorseDbContext`, the abstract `NorseDbContext` base, snake_case naming machinery every Norse context inherits, and **the provider seam itself** — `INorseEfProvider`/`INorseEfMigrationProvider` (the tier split: a marker interface with no new members, so registering a non-migration-capable provider like a future SQLite binding against a migration host is a compile error), `NorseNameRewriters` (`LowerSnakeCase`/`UpperSnakeCase`), `AddNorseContext<TContext>()` (pooled registration for runtime hosts), and `ApplyNorseProviderOptions()` (wires a provider's `Configure`/`NameRewriter`/`EntityRenameHook` into the context).
- `Norse.Persistence.EntityFramework.Migrations` — `EfMigrationContributor<TContext>`, `MigrationConnectionStringAttribute`, `AddNorseMigrationContext<TContext>()` (non-pooled — migration hosts run once and exit, pooled options are frozen), and — consolidated here from what used to be a per-provider generator pair — **the one provider-agnostic Roslyn `IIncrementalGenerator`**. It discovers every `EfMigrationContributor<TContext>`, every `ISeedContributor`, and the single provider binding visible in a migrations service's compilation, and emits `AddNorseMigrations()`, wiring `AddNorseMigrationsRunner()` and `AddNorseSeedingRunner()` (both Midgard, `Norse.Infrastructure.Migrations`) in the same generated call. It walks **compiled assembly symbols**, never source syntax trees, by design — proven identical whether contributor packages arrive as `ProjectReference` (Bifröst dev mode) or `PackageReference` (NuGet/CI mode). It reports five diagnostics, NORSE030–034: no provider binding referenced (030), more than one provider binding referenced (031), no `ModelSnapshot` found for a context so the migrations assembly can't be derived (032), more than one `ModelSnapshot` found so it's ambiguous (034, added during review — reference order must never decide it), and a provider binding missing its required `public static Instance` member (033). Reference this one package with `Generator="true"` from a migrations service.
- `Norse.Persistence.EntityFramework.Design` — `DdlEmittingMigrationsScaffolder` and `AddNorseDesignTimeServices()` (landed 2026-07-22, provider-agnostic — see the design doc for the mechanism), plus the one neutral `NorseDesignTimeDbContextFactory<TContext>` — abstract, with `protected abstract INorseEfProvider ProviderBinding { get; }` for a downstream factory to name its provider, and `protected abstract string DatabaseName { get; }`. Never connects to a database; deliberately no environment-variable escape hatch (the earlier `DOTNET_EFTOOLS_CONNECTIONSTRING` mechanism dies with the provider-specific factories it belonged to).
- `Norse.Persistence.EntityFramework.PostgreSQL` — `NorsePostgresEfProvider`, one sealed class, `public static Instance`, implementing `INorseEfMigrationProvider`: `UseNpgsql` wiring, Aspire enrichment, engine-native lower snake_case (`NameRewriter => NorseNameRewriters.LowerSnakeCase`), inert design-time placeholder connection string.
- `Norse.Persistence.EntityFramework.SqlServer` — `NorseSqlServerEfProvider`, same shape: `UseSqlServer` wiring with a forced (not opt-in) compatibility-level-170 floor, raw PascalCase (`NameRewriter` is `null` — SQL Server's engine-native default needs no rewriter), and the temporal history-table rename hook wired against that null rewriter — inert by construction, since `ApplyNorseProviderOptions()` only wires `EntityRenameHook` into the naming convention when `NameRewriter` is non-null.

The spec's acceptance test: Oracle or SQLite arrives as one more thin binding package (like `.PostgreSQL`/`.SqlServer` above), zero edits to the neutral foundation.

Three provider-aware conventions carried through the repackaging unchanged in behavior, only in where they're expressed: `[FixedLength(n)]` still only translates to `.IsFixedLength()` on SQL Server (Postgres's own docs say `character(n)` has no storage/performance benefit over `character varying(n)` there); snake_case naming is now expressed as each provider binding's `NameRewriter` delegate rather than an `AddNorse{Provider}Context` extension's `useSnakeCaseNaming` opt-in/opt-out parameter — that parameter ceases to exist because the extension methods carrying it are deleted along with the provider-specific registration surface, and the naming decision moves to binding data; and `NorseModelConventions.Apply()` still registers the provider-correct `SequentialGuid` byte-order converter — `SqlServerSequentialGuidValueConverter` on SQL Server, `Rfc9562SequentialGuidValueConverter` everywhere else — this realm's first real code dependency on Svartálfheim's `Norse.Primitives` (`SequentialGuid`/`GuidByteOrder`), landed 2026-07-26 (`../Glitnir/docs/Urdarbrunnr/specs/2026-07-26-sequentialguid-provider-aware-ef-converter-design.md`).

Snake_case naming itself, previously provided by the external `EFCore.NamingConventions` package, remains implemented in-house via `NorseSnakeCaseNamingConvention` and `SnakeCaseNameRewriter` in `Norse.Persistence.EntityFramework`. It still carries the two hardening fixes from 2026-07-23, found downstream in Mímisbrunnr and load-bearing for every Postgres+snake_case realm: the EF migrations-history table is excluded from renaming entirely (its raw-SQL-facing `HistoryRepository.TableName` never went through this convention, so renaming it desynced `LOCK TABLE`/`CREATE TABLE` and 42P01'd on first migrate), and only a JSON-mapped entity's own **root** container column is renamed — a nested JSON entity sharing that container used to get renamed too, which crashes EF Core 11 preview6's JSON query shaper (the identical, already-fixed-elsewhere bug behind `dotnet/efcore#37417`). Full design: `../Glitnir/docs/Urdarbrunnr/specs/2026-07-22-inhouse-snake-case-naming-convention-design.md` (see its 2026-07-23 addendum) and `../Glitnir/docs/Urdarbrunnr/specs/2026-07-22-design-time-ddl-emission-and-chassis-rename-design.md`.

**The generator's consolidated home is a move, not a new capability.** This realm's first Roslyn `IIncrementalGenerator` still shipped as part of the four-assembly `Design.PostgreSQL` package on 2026-07-22 — that historical credit stands. The provider-seam repackaging deleted `Design.PostgreSQL`/`Design.SqlServer` and their two separate generators outright and consolidated the one generator, made fully provider-agnostic, into `.Migrations` — the mechanism the credit describes didn't change; where it lives did.

**Landed 2026-07-28:** the §11 adoption sweep across Himinbjörg, Mímisbrunnr, and Yggdrasil onto this seam is implemented, each on its own local `feature/ef-provider-seam-adoption` branch. Bifröst's dev-mode composition of the migrations path is green again, and the AppHost live gate — run from wiped volumes — stood up both `norse_identity` (full Identity v3 + OpenIddict schema) and `norse_reference` (UN M49 seed data) end to end. Realm merges, tags, and releases are the human's ship gates and remain outstanding.

This is the realm's proving ground for compile-time enforcement over runtime guessing: the generator is live proof the pattern survives contact with both reference modes, not just the happy path.
