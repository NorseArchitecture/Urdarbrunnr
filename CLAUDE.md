## 1. What This Repository Is

Urðarbrunnr is **the well's record** — `Norse.Persistence`: the platform's persistence realm, scoped to all database and data-store activity, not just EF Core. `Norse.Persistence.EntityFramework` is today's live vendor family — entity base types, `DbContext` foundations, conventions, value converters, and the migrations chassis, the EF Core foundation that Midgard's concrete repository implementations ride on, governed by the contracts Asgard declares — but it is one branch, not the ceiling. A different ORM (Dapper, NHibernate, SqlSugar), a native driver that bypasses an ORM entirely, or a document/search store (MongoDB, Elasticsearch) lands here the same way Heimdall took on FluentUI: drop in the vendor-specific `.csproj` and package references as a sibling under `Norse.Persistence.*` (`Norse.Persistence.Dapper`, `Norse.Persistence.MongoDB`, …), wire it up, done — no separate realm, no new repo. In the dependency chain it sits below Asgard and Svartálfheim, and above Midgard.

**Five assemblies are live**, built around a provider seam (`../Glitnir/docs/Urdarbrunnr/specs/2026-07-27-ef-provider-seam-repackaging-design.md`), the repackaging that superseded the four-plus-per-provider-generator shape shipped as Tasks 3–6 of the cross-realm migrations framework rollout (`../Glitnir/docs/Platform/plans/2026-06-28-migrations-framework-identity-schema.md`):

- `Norse.Persistence.EntityFramework` — the neutral foundation: `INorseDbContext`, the abstract `NorseDbContext` base, snake_case naming machinery every Norse context inherits, the temporal opt-in surface (`ITemporalEntity`, `NorseAnnotationNames`, `TemporalEntityConvention`, `TemporalParkedOnSqlServer()` — see the temporal section below), and **the provider seam itself** — `INorseEfProvider`/`INorseEfMigrationProvider` (the tier split: a marker interface with no new members, so registering a non-migration-capable provider like a future SQLite binding against a migration host is a compile error), `NorseNameRewriters` (`LowerSnakeCase`/`UpperSnakeCase`), `AddNorseContext<TContext>()` (pooled registration for runtime hosts), and `ApplyNorseProviderOptions()` (wires a provider's `Configure`/`NameRewriter`/`EntityRenameHook`/`TemporalRealizationHook` into the context).
- `Norse.Persistence.EntityFramework.Migrations` — `EfMigrationContributor<TContext>`, `MigrationConnectionStringAttribute`, `AddNorseMigrationContext<TContext>()` (non-pooled — migration hosts run once and exit, pooled options are frozen), and — consolidated here from what used to be a per-provider generator pair — **the one provider-agnostic Roslyn `IIncrementalGenerator`**. It discovers every `EfMigrationContributor<TContext>`, every `ISeedContributor`, and the single provider binding visible in a migrations service's compilation, and emits `AddNorseMigrations()`, wiring `AddNorseMigrationsRunner()` and `AddNorseSeedingRunner()` (both Midgard, `Norse.Infrastructure.Migrations`) in the same generated call. It walks **compiled assembly symbols**, never source syntax trees, by design — proven identical whether contributor packages arrive as `ProjectReference` (Bifröst dev mode) or `PackageReference` (NuGet/CI mode). It reports five diagnostics, NORSE030–034: no provider binding referenced (030), more than one provider binding referenced (031), no `ModelSnapshot` found for a context so the migrations assembly can't be derived (032), more than one `ModelSnapshot` found so it's ambiguous (034, added during review — reference order must never decide it), and a provider binding missing its required `public static Instance` member (033). Reference this one package with `Generator="true"` from a migrations service.
- `Norse.Persistence.EntityFramework.Design` — `DdlEmittingMigrationsScaffolder` and `AddNorseDesignTimeServices()` (landed 2026-07-22, provider-agnostic — see the design doc for the mechanism), plus the one neutral `NorseDesignTimeDbContextFactory<TContext>` — abstract, with `protected abstract INorseEfProvider ProviderBinding { get; }` for a downstream factory to name its provider, and `protected abstract string DatabaseName { get; }`. Never connects to a database; deliberately no environment-variable escape hatch (the earlier `DOTNET_EFTOOLS_CONNECTIONSTRING` mechanism dies with the provider-specific factories it belonged to).
- `Norse.Persistence.EntityFramework.PostgreSQL` — `NorsePostgresEfProvider`, one sealed class, `public static Instance`, implementing `INorseEfMigrationProvider`: `UseNpgsql` wiring, Aspire enrichment, engine-native lower snake_case (`NameRewriter => NorseNameRewriters.LowerSnakeCase`), inert design-time placeholder connection string, and — since 2026-08-05 — the three `ReplaceService` calls that are the whole PostgreSQL temporal seam (`NorseNpgsqlAnnotationProvider`, `NorseNpgsqlMigrationsAnnotationProvider`, `NorseNpgsqlMigrationsSqlGenerator`, plus `TemporalSqlEmitter`). `TemporalRealizationHook` is `null` here on purpose — Postgres realizes temporality in migration SQL, never in the model.
- `Norse.Persistence.EntityFramework.SqlServer` — `NorseSqlServerEfProvider`, same shape: `UseSqlServer` wiring with a forced (not opt-in) compatibility-level-170 floor, raw PascalCase (`NameRewriter` is `null` — SQL Server's engine-native default needs no rewriter), the temporal history-table rename hook wired against that null rewriter — inert by construction, since `ApplyNorseProviderOptions()` only wires `EntityRenameHook` into the naming convention when `NameRewriter` is non-null — and the `TemporalRealizationHook` that turns the Norse marker into EF-native `IsTemporal()`.

The spec's acceptance test: Oracle or SQLite arrives as one more thin binding package (like `.PostgreSQL`/`.SqlServer` above), zero edits to the neutral foundation.

Three provider-aware conventions carried through the repackaging unchanged in behavior, only in where they're expressed: `[FixedLength(n)]` still only translates to `.IsFixedLength()` on SQL Server (Postgres's own docs say `character(n)` has no storage/performance benefit over `character varying(n)` there); snake_case naming is now expressed as each provider binding's `NameRewriter` delegate rather than an `AddNorse{Provider}Context` extension's `useSnakeCaseNaming` opt-in/opt-out parameter — that parameter ceases to exist because the extension methods carrying it are deleted along with the provider-specific registration surface, and the naming decision moves to binding data; and `NorseModelConventions.Apply()` still registers the provider-correct `SequentialGuid` byte-order converter — `SqlServerSequentialGuidValueConverter` on SQL Server, `Rfc9562SequentialGuidValueConverter` everywhere else — this realm's first real code dependency on Svartálfheim's `Norse.Primitives` (`SequentialGuid`/`GuidByteOrder`), landed 2026-07-26 (`../Glitnir/docs/Urdarbrunnr/specs/2026-07-26-sequentialguid-provider-aware-ef-converter-design.md`).

Snake_case naming itself, previously provided by the external `EFCore.NamingConventions` package, remains implemented in-house via `NorseSnakeCaseNamingConvention` and `SnakeCaseNameRewriter` in `Norse.Persistence.EntityFramework`. It still carries the two hardening fixes from 2026-07-23, found downstream in Mímisbrunnr and load-bearing for every Postgres+snake_case realm: the EF migrations-history table is excluded from renaming entirely (its raw-SQL-facing `HistoryRepository.TableName` never went through this convention, so renaming it desynced `LOCK TABLE`/`CREATE TABLE` and 42P01'd on first migrate), and only a JSON-mapped entity's own **root** container column is renamed — a nested JSON entity sharing that container used to get renamed too, which crashes EF Core 11 preview6's JSON query shaper (the identical, already-fixed-elsewhere bug behind `dotnet/efcore#37417`). Full design: `../Glitnir/docs/Urdarbrunnr/specs/2026-07-22-inhouse-snake-case-naming-convention-design.md` (see its 2026-07-23 addendum) and `../Glitnir/docs/Urdarbrunnr/specs/2026-07-22-design-time-ddl-emission-and-chassis-rename-design.md`.

**The generator's consolidated home is a move, not a new capability.** This realm's first Roslyn `IIncrementalGenerator` still shipped as part of the four-assembly `Design.PostgreSQL` package on 2026-07-22 — that historical credit stands. The provider-seam repackaging deleted `Design.PostgreSQL`/`Design.SqlServer` and their two separate generators outright and consolidated the one generator, made fully provider-agnostic, into `.Migrations` — the mechanism the credit describes didn't change; where it lives did.

**Landed 2026-07-28:** the §11 adoption sweep across Himinbjörg, Mímisbrunnr, and Yggdrasil onto this seam is implemented, each on its own local `feature/ef-provider-seam-adoption` branch. Bifröst's dev-mode composition of the migrations path is green again, and the AppHost live gate — run from wiped volumes — stood up both `norse_identity` (full Identity v3 + OpenIddict schema) and `norse_reference` (UN M49 seed data) end to end. Realm merges, tags, and releases are the human's ship gates and remain outstanding.

**Landed 2026-08-05 — temporal (system-versioned) tables are a chassis capability, not hand-rolled SQL.** Design: `../Glitnir/docs/Platform/specs/2026-08-04-temporal-tables-persistence-chassis-design.md`; plan sibling in `../Glitnir/docs/Platform/plans/`. Section references below are that spec's.

- **Opt-in is one marker, provider-neutral.** `ITemporalEntity` is an empty interface in `Norse.Persistence.EntityFramework` — no members, ever: `system_period` never enters the CLR type, a wire `[DataContract]`, or a WASM payload (§2.1). Adoption is two acts and nothing else: add `: ITemporalEntity` to the entity and run `dotnet ef migrations add` (§5). No `MigrationBuilder` extension calls, no remembered mirror call, in any adopting realm — brownfield tables take the same path as greenfield ones.
- **`TemporalEntityConvention` is the one validation point**, registered by `NorseModelConventions.Apply` beside `RequireExplicitLengthConvention` and `RequireEntityConfigurationConvention`. At model finalize each marked entity must have a primary key and must not be owned or JSON-mapped, and its derived names are **reserved** — a model whose tables claim `{table}_history`, `{table}_timeline`, or `{Table}History` throws by name at startup rather than colliding late at migration time (§2.2). Validated entities are stamped `Norse:Temporal` (`NorseAnnotationNames`, public because it is seam surface the provider packages read, like EF's own `RelationalAnnotationNames`).
- **Stamp-then-realize, in one pass.** Immediately after each stamp the convention invokes the binding's `INorseEfProvider.TemporalRealizationHook`, mirroring how `EntityRenameHook` rides the naming convention. This is not a style choice: plugin-added finalizing conventions enter EF's finalizing list *before* context-added ones, so a realization convention registered independently would read the annotation before the stamp exists. The hook reaches `NorseDbContext.ConfigureConventions` through `NorseTemporalRealizationOptionsExtension` — deliberately **carrier-only**: it applies no services and registers no convention-set plugin, and exists purely to move a delegate from `ApplyNorseProviderOptions()` to the context. Like `NameRewriter`, the hook has no default — every binding states its posture rather than silently inheriting a no-op.
- **SQL Server realizes in the model.** `NorseSqlServerEfProvider`'s hook sets EF-native `IsTemporal(true)`, the period shadow properties `SystemPeriodStart`/`SystemPeriodEnd` (rhyming with Postgres's `system_period`, replacing EF's bare `PeriodStart`/`PeriodEnd`), and history table `{Table}History` (EF's default, kept) — §4. **Split-table + temporal is a model-finalize error on SQL Server**, dismissible only by declaring `TemporalParkedOnSqlServer()` in the entity's static `Configure`, which skips temporality **on SQL Server only** and leaves PostgreSQL fully temporal. Himinbjörg's user entity is both split and temporal and one model builds for both providers, so a hard throw would brick the SQL Server migrations assembly and a silent skip would break fail-loud law; a greppable declared divergence is the middle. **Re-entry trigger: delete the park the day [dotnet/efcore#26457](https://github.com/dotnet/efcore/issues/26457) ships per-fragment temporal control** (the migration-generation NRE behind it is [dotnet/efcore#30366](https://github.com/dotnet/efcore/issues/30366)).
- **PostgreSQL realizes nothing in the model — everything rides migration SQL generation, through three seams**, all `ReplaceService`'d unconditionally in `NorsePostgresEfProvider.Configure` (temporality is opted into per entity, never per registration): `NorseNpgsqlAnnotationProvider` (`IRelationalAnnotationProvider`) projects the marker onto the relational table so EF's differ emits usable create/alter operations at all — and only onto the entity's **root** table, so a split fragment never inherits it; target-model consultation inside `NorseNpgsqlMigrationsSqlGenerator.Generate` identifies the table for ordinary column operations, which carry no marker; and `NorseNpgsqlMigrationsAnnotationProvider` overrides `IMigrationsAnnotationProvider.ForRemove(ITable)` for the drop side, where the entity has left the target model and `DropTableOperation` was measured to carry no annotations at all. The first two are the emission-seam spike's verdict (`../Glitnir/poc/ef-temporal-emission/FINDINGS.md`); the third was measured afterwards for the one shape the spike never scaffolded.
- **The apparatus is Norns Model B**, emitted by `TemporalSqlEmitter` — one method per element of §3.1, every method a complete self-contained block that touches no EF metadata, so the same text serves create, transitions, and evolution: `system_period tstzrange` on the main table, `{table}_history` under a `PRIMARY KEY (…, system_period WITHOUT OVERLAPS)`, a `SECURITY DEFINER` versioning function (`search_path` pinned to `pg_catalog`, every reference schema-qualified, `EXECUTE` revoked from `PUBLIC`), UPDATE/DELETE triggers, and a `{table}_timeline` view (explicit column lists, never `SELECT *`).
- **PG19 is a floor asserted in-migration, never documented-and-hoped.** The prelude — a `server_version_num >= 190000` assert and an idempotent `btree_gist` guard that raises a named provisioning-prerequisite diagnostic when the migration role may not `CREATE EXTENSION` — is emitted **once per migration batch**, at the first temporal table, not per table. A conditional third assert rides it: when neither the operation nor the model named a schema, the apparatus is qualified with `public` while Npgsql emits the main table unqualified, so the migration asserts `current_schema() = 'public'` up front rather than letting a table and its apparatus land in two schemas. Evolution paths deliberately skip the prelude — the floor was asserted by the migration that built the apparatus, and a mis-aimed mirror statement fails on its own missing relation.
- **`now()` appears nowhere.** The clock is `clock_timestamp()` everywhere — insert default and trigger alike — with the monotonicity clamp (`greatest(clock_timestamp(), lower(OLD.system_period) + 1 microsecond)`) so every history period has strictly positive length regardless of NTP behavior, and no-op suppression (`OLD` vs `NEW` over the explicit application column list) so a no-change UPDATE writes no history row and leaves `system_period` untouched. §3.2 is the whole argument; the short version is that `now()` is transaction-start time, and closing a version with it mints `empty` ranges the temporal PK silently admits in duplicate.
- **Transitions and evolution both ship** (§3.3–§3.4). Enable on an existing table adds the column nullable, backfills every pre-existing row from a **single** captured `clock_timestamp()` (a volatile per-row default would scatter open bounds across the table rewrite), then takes `NOT NULL` and the standing default; history starts empty, honestly. Disable and dropping the entity are the same act — visible destruction as plain statements in the scaffolded diff, never behind a helper. `AddColumn`/`DropColumn`/`RenameColumn`/`AlterColumn` each emit in the fixed drop-view-first order (drop view, main operation, history mirror, `CREATE OR REPLACE FUNCTION`, `CREATE VIEW` afresh) — the only appliable order, since PostgreSQL blocks column drops and type changes under a dependent view and `CREATE OR REPLACE VIEW` cannot change the output column set. History mirrors **name and store type only**, nullable whatever the main column declares, never a default/identity/generation/constraint/index. `RenameTable` is the fifth shape and the one exception to that order: PostgreSQL keeps a renamed table's triggers under their old names still bound to the old function, so the choreography renames both tables in place (preserving the history data mapping) and then explicitly retires and recreates every derived apparatus object. Multi-operation batches are grouped per table by target name — EF sorts a dropped column ahead of its table's rename and an added one after it, and those are one table's evolution, not two.
- **What the generator refuses, it refuses by name, before emitting a line of SQL.** A marker transition combined with any column operation on the same table (EF orders the two independently, so one direction always runs against a shape that does not exist yet — scaffold the transition as its own migration); a primary-key change on a temporal table; a schema move. Each diagnostic names the sanctioned path: drop temporality (visible destruction), make the change, re-mark — or hand-author the migration for the rare case that must preserve history across it. Silently-wrong history constraints are the one outcome this design will not ship.
- **Proof is chassis-out, no mocked databases.** Snapshot suites drive EF's *real* model differ over two real models and the real generator (`TemporalCreateTableSqlTests`, `TemporalTransitionSqlTests`, `TemporalEvolutionSqlTests`); `TemporalEvolutionLiveTests` applies every evolution shape to a real server with a live history row and a live view, so snapshot-green-but-unappliable DDL cannot ship; and `TemporalApparatusIntegrationTests` is the 13-fact §3.2 semantics suite — one clock, the clamp, no-op suppression, version closure, fragment-only updates writing no history, and the brownfield transitions against live data. All live tests share one `postgres:19beta2` Testcontainers fixture, the same image Bifröst's AppHost runs. **Deviation from spec §6 item 3, recorded:** these live tests landed in the existing `Persistence.EntityFramework.PostgreSQL.Tests` project rather than a new one. SQL Server coverage stays model-level (`SqlServerTemporalRealizationTests`) — no SQL Server container fixture exists anywhere on the platform, and standing one up is its own chore, deliberately not smuggled into this train.
- **Downstream is not this realm's gate.** Himinbjörg's identity enablement and Bifröst's primary+replica proof are the design's remaining exit criteria and belong to those realms.

This is the realm's proving ground for compile-time enforcement over runtime guessing: the generator is live proof the pattern survives contact with both reference modes, not just the happy path.
